# Pit Wall

**Season context, results and race analysis for Formula 1, from 1950 to the current season.**

Pit Wall is a full-stack F1 data app: a FastAPI backend that collects, cleans, caches and analyses data from three public sources, and a React frontend that turns it into a race-weekend dashboard. It answers two questions: *what is happening this season?* and *why did that race go the way it did?*

> Unofficial fan project. Not affiliated with Formula 1, the FIA or any team.

---

## About

The official app and timing sites show raw numbers. Pit Wall adds the context around them:

- **Race weekend at a glance.** Next race with a live countdown, the weekend schedule in your own time zone, the last podium and the title fight.
- **Title maths.** The gap to the leader, the points still available, and whether the title can be sealed this weekend (sprints counted).
- **Race analyst.** Lap-by-lap commentary for a race (headline, key battles, strategy watch, biggest mover). It is generated by deterministic rules from timing data, with no language model involved.
- **Telemetry.** Lap positions, lap times, tyre stints, pit stops and fastest-lap speed, throttle, brake and gear traces.
- **Head-to-head.** Two drivers, or two constructors car by car, across a whole season.
- **History.** Standings, results, points progression and calendars for every season since 1950, picked by decade, year or search.

Data limits are shown honestly. Seasons without reachable timing data, and races not yet published, read "not available yet" instead of breaking the page.

The project is also a portfolio piece for data engineering and analytics: ingestion from rate-limited APIs, normalising two telemetry sources into one schema, a data-driven caching policy, a precomputed serving store, a scheduled job, and an offline DuckDB + dbt warehouse.

## Data sources

| Source | What it provides | Seasons |
|---|---|---|
| [Jolpica F1 API](https://github.com/jolpica/jolpica-f1) (Ergast-compatible) | Schedules, results, qualifying, sprints, standings, pit stops, drivers, constructors, circuits | 1950 → now |
| [FastF1](https://github.com/theOehrly/Fast-F1) | Lap timing, stints, race control messages, car telemetry | 2021–2022 (see below) |
| [OpenF1](https://openf1.org) | The same timing and telemetry for recent seasons | 2023 → now |

F1's own live-timing archive now refuses every request, so FastF1 can only load the seasons its community mirror hosts (2021–2022). OpenF1 covers 2023 onward. 2018–2020 have no reachable timing data, and the app says so.

## Data engineering workflow

### 1. Ingest: rate-limited APIs, fetched once

- **Jolpica** (`backend/ergast.py`). Every request goes through one function, `_get()`, which stores the raw JSON in SQLite (`api_cache.sqlite`) keyed by URL.
  - Failures are classified at the source: a 404 means no data, a 429 means rate limited, a timeout or bad JSON means the upstream is broken. Each becomes a clear API error instead of a crash.
  - If Jolpica is down or rate-limiting, an expired cached copy is served instead of an error.
  - Jolpica returns at most 100 rows per request, so long lists (early-1950s seasons) are fetched page by page.
- **OpenF1** (`backend/openf1.py`). Calls are spaced 0.35 s apart to stay under the free tier's 3 requests/s and 30/min. OpenF1 has no round numbers, so a race is matched by its start time from the Jolpica schedule.
- **FastF1** (`backend/telemetry.py`). Sessions load from FastF1's own disk cache after the first download.

### 2. Cache freshness decided by the data, not a fixed timer

`backend/cache_policy.py` decides how long each cached response stays valid, at the moment it is read:

| Data | Lifetime |
|---|---|
| Past seasons | Never expire |
| A finished round with data (race started more than 6 h ago) | Never expires |
| That round while still empty | Retried hourly |
| Anything during a live race weekend | 5 minutes |
| Everything else | 1 hour |

So historical data is fetched once, and a live weekend refreshes quickly without hammering the API.

### 3. Normalise two telemetry sources into one schema

FastF1 (2021–22) and OpenF1 (2023+) describe the same race differently. `telemetry.py` maps both into one JSON shape, so the frontend never knows which source it got:
- lap positions come from the order cars cross the line;
- OpenF1 speed traces have no distance, so distance is integrated from speed;
- brake is mapped to the same 0/1 scale;
- the grid comes from Jolpica when the source's grid is empty;
- team colours are filled from one table when the source leaves them blank.

Response models in `schemas.py` describe every route's JSON exactly. A smoke check (`scripts/smoke_check.py`) diffs every route's status and JSON shape against a saved baseline.

### 4. Precompute heavy results into a serving store

A cold race analysis takes 20 s or more. `precomputed.py` keeps finished payloads in DuckDB (`precomputed.duckdb`, table `race_payloads`), so those routes answer in milliseconds:
- **Scheduler** (`jobs/scheduler.py`, APScheduler inside the API): one job per race of the current season, 5 hours after its start. It re-plans daily and catches up a run missed within the last day.
- **CLI** (`python -m jobs.precompute --season 2022 --round 16`) for past races.
- DuckDB allows one writer per file, so the API owns the file. When the API is running, the CLI hands the write to it over a localhost-only endpoint.
- If a race isn't stored, the route computes it live and returns identical JSON.

### 5. Offline warehouse: DuckDB + dbt

`backend/warehouse/` is a separate batch pipeline for all-time history:

1. **Ingest** (`ingest/ingest_jolpica.py`) loads raw tables into `warehouse/db/f1.duckdb`: `raw_schedule`, `raw_results`, `raw_qualifying`, `raw_pitstops`, `raw_driver_standings`.
   - Each season is deleted and reloaded, so re-running it is safe.
   - Lists longer than Jolpica's 100-row pages are followed page by page (1953 has 108 drivers).
   - On a rate limit, the job waits and carries on instead of failing the season.
2. **Transform with dbt** (`dbt_f1/`):
   - `staging` (views): typed, renamed columns and flags such as `is_win`, `is_podium`, `is_dnf`, `is_classified`.
   - `intermediate`: per-driver-season and career aggregates, and circuit history.
   - `marts` (tables): `mart_driver_profile`, `mart_constructor_profile`, `mart_circuit_profile`, with career wins, podiums, points per race, average finish, positions gained and championships.
3. **Query** the marts with DuckDB (`duckdb warehouse/db/f1.duckdb`) or any SQL client.

The live API does not depend on the warehouse. It is the analytics layer for career-level questions.

## Analytics workflow

| Analysis | Where | How it works |
|---|---|---|
| Race analyst | `backend/race_analyst.py` | For each lap: leader and gap, battles under a time threshold, undercut chances and overdue stints, biggest mover. All thresholds are named constants, each with a test on both sides of its boundary. |
| Title maths | `frontend/src/lib/titleMath.js` | Points still available (25 per GP, plus 8 per sprint), whether the title is sealed, and whether the leader can seal it this weekend. |
| Head-to-head | `backend/services/h2h.py` | Season aggregates for two drivers; for constructors, each round goes to the team whose best car finished ahead. |
| Points progression | `ergast._progression` | Points after every round per entrant, with totals carried over rounds they missed. |
| Race summary tiles | Telemetry page | Laps under neutralisation, fastest laps, pit-stop distribution, places gained. |

Edge cases are handled deliberately: unclassified finishers use position 99, constructors excluded from a championship (Tyrrell 1985, McLaren 2007) are kept, and lapped cars read "+N laps".

## Tech stack

- **Backend:** Python 3.12/3.13, FastAPI, pydantic-settings, requests, FastF1, pandas, DuckDB, APScheduler, SQLite

## Quick start

**Both servers at once:** `./start.sh` (Linux/macOS) or `powershell -ExecutionPolicy Bypass -File .\start.ps1` (Windows).

**Backend** (from `backend/`):
```bash
python -m venv venv                       # Windows: py -3.13 -m venv venv
venv/bin/python -m pip install -r requirements.txt   # Windows: venv\Scripts\python
venv/bin/python -m uvicorn main:app --reload --port 8000
```
API docs at http://127.0.0.1:8000/docs.

**Frontend** (from `frontend/`):
```bash
npm install
npm run dev        # http://localhost:5173, proxies /api to the backend
```

**Docker:** `docker compose up --build` (not run-tested yet).

**Warehouse** (optional, from `backend/`):
```bash
venv/bin/python -m pip install -r warehouse/requirements.txt
cd warehouse/ingest && python ingest_jolpica.py --seasons 2024-2025
cd ../dbt_f1 && dbt run --profiles-dir .
```

Configuration (environment variables or `backend/.env`, see `.env.example`): `CORS_ORIGINS`, `DEFAULT_SEASON`, `CACHE_DIR`, `LOG_LEVEL`, `PRECOMPUTE_ENABLED`, `PRECOMPUTE_DELAY_HOURS`, `API_URL`, `TELEMETRY_SEASONS`.

## Tests

```bash
cd backend
venv/bin/python -m pip install -r requirements-dev.txt
venv/bin/python -m pytest      # ~1 s, never touches the network
venv/bin/ruff check . && venv/bin/ruff format --check .
```

Tests replay recorded API responses (`tests/fixtures/`); `scripts/record_fixtures.py` re-records them. CI runs lint, tests and the frontend build on every push.

```
  jobs/              precompute scheduler and CLI
  warehouse/         offline ingest + dbt project
  tests/             pytest suite + recorded fixtures
frontend/
  src/pages/         Home, Results, Head-to-head, Telemetry, Standings, Calendar
  src/components/    header, season picker, podium, standings rows, charts

```
